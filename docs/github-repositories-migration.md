## Data compatibility notes

`github.json` remains the shared VS Code schema and location. The implementation preserves unrecognized fields and existing repository records. Writes use a mode-restricted sibling temporary file and atomic replacement. A persistent `github.json.lock` sidecar coordinates IntelliJ instances; because VS Code does not use that lock, the store also compares exact file bytes immediately before replacement and reports observed external edits as conflicts. This is stricter than the current VS Code store, which serializes only in-process writes. As with any writer that does not share a lock protocol, an external write in the tiny interval after the final comparison cannot be prevented.

Behavior notes: VS Code search delegates to its tree search command; the IDEA search field, filter logic, and action were removed from the tool window per user request. The target opens visibility and language groups initially, and its expand/collapse state is global for language groups; VS Code's asynchronous expand-all reveal includes a retry for tree refresh races. The source settings command opens the VS Code extension settings page; IntelliJ provides a GitHub settings form in the tool window and exposes its operations as Find Actions. Repository URL identity preserves owner/repository path case and only folds the host, matching `repositoryIdentityKey`. The target validates the config structure at runtime but does not bind IntelliJ's JSON editor to the source JSON Schema. HTTPS proxy endpoints and proxy URLs containing credentials are accepted as configuration values but are not transport-compatible yet; use a plain HTTP proxy or SOCKS proxy for GitHub API requests. The clone completion path publishes a project-data event so an already-open Projects tool window reloads the newly added project.

`repos.json` remains in VS Code's `{ "version": 1, "repos": [...], "settings": ... }` shape. `project.json` is written through the existing Project Atlas project service/store.
